# 객체지향 생활 체조 적용 기준

객체가 자신의 데이터와 행동을 책임지도록 설계한다. 작은 객체와 명확한 이름으로 변경 이유를 드러내는 것이 목적이다.

## 학습 근거

Jeff Bay의 Object Calisthenics는 작은 프로젝트에 엄격한 제약을 적용하는 설계 훈련이다.
훈련 후에는 원칙을 설계 판단에 활용하도록 설명한다.
[저자 에세이 공개 사본](https://www.bennadel.com/resources/uploads/2012/ObjectCalisthenics.pdf),
[출판사 목차: The ThoughtWorks Anthology 6장](https://media.pragprog.com/titles/twa/toc.pdf).
에세이는 저자명이 표시된 외부 보관본이며, 출판사 목차로 저자와 수록 사실을 대조했다.

## 9가지 원칙과 플러그패스 적용

첫 열은 원문 원칙의 요약이며, 나머지는 프로젝트에 적용할 판단이다.

| 원칙 | 적용할 방법 |
| --- | --- |
| 메서드의 들여쓰기는 한 단계 | 중첩된 순회·조건에서 의미 있는 작업을 분리한다. |
| else를 사용하지 않는다 | 조기 반환으로 조건을 정리하고, 반복되는 상태별 행동은 적절한 객체로 옮긴다. 삼항 연산자로 숨기지 않는다. |
| 기본형과 문자열을 감싼다 | 식별자·출력 단위처럼 혼동되거나 검증 규칙이 있는 도메인 값을 타입으로 표현한다. |
| 일급 컬렉션을 사용한다 | 후보 집합의 중복·선택 규칙을 컬렉션 객체에 모은다. 내부 가변 목록을 그대로 반환하지 않는다. |
| 한 줄에 점 하나 | 다른 객체의 내부를 연쇄 탐색해 판단하지 않고 책임을 가진 객체에 요청한다. |
| 이름을 축약하지 않는다 | `st`, `chg` 같은 임의 축약 대신 도메인 의미를 드러낸다. |
| 객체를 작게 유지한다 | 메서드는 한 작업을, 클래스는 응집된 책임을 맡는다. 크기가 커지면 책임을 다시 살핀다. |
| 인스턴스 변수는 두 개 이하 | 세 개부터 서로 다른 책임이 섞였는지 검토한다. 숫자만 맞추기 위한 묶음 객체는 만들지 않는다. |
| getter·setter·property를 사용하지 않는다 | 무조건적인 상태 변경 API를 피하고, 의미 있는 행동과 판단을 객체에 둔다. |

## 직관: 상태를 꺼내 판단하던 코드를 어디로 옮기는가

향후 충전소 데이터 최신성 판단에 적용할 개념 예시다. 아래 이름은 아직 구현된 API가 아니다.

```text
외부에서 관측 시각을 꺼내 여러 곳에서 최신성 계산
                       ↓ 책임 이동
관측 객체에 isFreshAt(기준 시각, 허용 시간)을 요청
```

관측 객체가 시각의 의미와 경계 조건을 소유하면, 허용 시간이 바뀌거나 잘못된 시각이 들어올 때 수정할 위치가 분명해진다.
서비스는 그 판단을 받아 다음 작업을 조율한다. 이름만 바꾼 getter로 기존 계산을 외부에 남겨두면 책임은 이동하지 않은 것이다.

## 적용 범위와 예외

업무 도메인 코드에 우선 적용한다. 원문의 엄격한 훈련 규칙을 프로젝트 전체에 일괄 강제하는 방식은 아니다.

- DTO·설정·프레임워크 경계에는 직렬화와 연동에 필요한 기본형·접근자를 허용한다. 업무 판단을 그 경계에 몰아넣지는 않는다.
- 빌더·Stream·테스트 assertion의 연속 호출은 다른 도메인 객체의 내부를 파고드는 호출과 구분한다.
- 객체 크기·필드 수는 책임을 검토하는 기준이다. 원문의 클래스 50줄·패키지 10파일은 훈련 기준이며 현재 빌드 제한은 아니다.
- 불변 값이나 판단 결과를 반환하는 의미 있는 조회는 허용한다. 데이터를 읽는 모든 메서드를 제거하지 않는다.
  이 판단은 데이터와 행동의 배치를 중시하면서 유용한 조회도 인정하는 [Martin Fowler의 설명](https://martinfowler.com/bliki/TellDontAsk.html)을 참고했다.

예외가 필요하면 대상·이유·보완 검증을 변경 설명에 남긴다. 규칙 적용 여부는 객체의 책임과 불변조건이 더 명확해지는지로 평가한다.

## 현재 코드에 대조한 결과

| 대상 | 확인과 적용 판단 |
| --- | --- |
| `PlugPassApplication` | 13줄이며 애플리케이션 시작만 담당한다. 분리할 업무 책임이나 가변 상태가 없다. |
| `PlugPassApplicationTests` | 46줄이며 포트 주입과 실제 HTTP 응답 검증을 담당한다. 포트·응답 문자열은 테스트 경계 값으로 유지한다. |
| 테스트의 `get(path)` | 객체의 필드 getter가 아니라 HTTP 요청 동작이다. 이름의 get만 보고 금지하지 않는다. |
| HTTP 빌더·JSON 해석·AssertJ | 테스트와 외부 API 사용 범위다. 점 개수를 줄이기 위한 중간 객체는 추가하지 않는다. |
| 업무 도메인 객체 | 아직 없다. 실제 기능 구현 시 위 원칙으로 설계하고 동작 테스트로 확인한다. |

생활 체조는 프로젝트 지침과 설계·리뷰 기준에 반영했다. JPA 검증용 엔티티는 식별자와 내용의 두 필드만 두고 setter 없이 생성하며, JPA 기본 생성자와 읽기 접근자는 테스트·영속성 경계의 예외로 둔다. 기존 코드에 줄 수나 점 개수만 맞추는 리팩터링은 하지 않았다.
자동 검사기가 9가지 원칙을 강제하는 상태는 아니다.

## 다음 기능의 리뷰와 검증

- 판단·변경은 어느 객체가 소유하는가? 외부에서 값을 꺼내 같은 규칙을 반복하지 않는가?
- 값 객체가 잘못된 입력·단위 혼동을 막는가? 단순 전달용 포장만 늘리지 않는가?
- 컬렉션의 중복·선택 규칙이 한 곳에 있는가? 반환된 목록으로 내부 상태를 바꿀 수 없는가?
- 중첩·분기·필드가 늘어난 이유를 설명할 수 있는가?
- 규칙을 어긴 동작을 테스트가 잡는가? 예를 들어 최신성 경계 시각, 잘못된 값, 외부 목록 변경을 실제로 검증한다.

지금은 리뷰 기준이다. 반복되는 위반이 확인되면 실제 실패를 잡는 최소한의 정적 검사나 계약 테스트를 추가한다.
