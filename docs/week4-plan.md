# 4주차 실행 계획 — T14 → T15

기준: plan.md·tasks.md의 승인된 4주차 범위. 기존 checkout의 별도 codex 브랜치에서 한 작업씩 구현·검증·PR·보호된 머지를 진행한다. 병렬 에이전트는 사용하지 않는다.

1. T14: 실제 공급자 fixture HTTP → 실제 수집/commit → 사용자 HTTP 검색·상세·제외 추천을 검증한다. 중복·관측 시각 누락·합성 관측 시각의 경과·503·복구·빈 결과를 분리한다. 업무 구현은 이미 존재하므로 신규 종합 테스트의 최초 통과는 기존 동작 확인이다.
2. T14 검사기: 통과한 suite만으로 HTTP 응답 산출물의 누락을 가릴 수 없게 필수 journey 증거를 확인한다. 검사기 회귀 assertion 실패 → 최소 구현 → 전체 공용 검증.
3. T15: 고정 생성 데이터 10,000/50,000·seed·시계·조회 분포·동시 사용자20·warmup30초·측정180초. 테스트 전용 서버와 Python 표준 라이브러리 부하 도구 하나를 사용한다. 운영 코드와 JAR에는 seed/측정 endpoint가 들어가지 않는다.
4. 정확성: 부하 전후 검색·상세·제외 추천 값 비교, 요청마다 HTTP/응답 계약 판정. 조회별 SQL 수는 경쟁 부하가 없는 별도 요청에서 Hibernate Statistics 차이로 측정한다. 목표 실패를 검증 실패와 구분해 원본 결과를 보존한다.
5. 기록: Red/Green/리뷰·실측 조건과 수치·대상 SHA·PR/CI/merge·cmux와 실공공 API 미확인 경계를 남긴다. 성능 개선은 T16 범위이므로 이번 작업에서 앞당기지 않는다.

의존 계약: T14의 정확성 assertion을 T15에서 유지하며, T14 main 반영 후 T15를 시작한다. 현재 cmux 환경변수 없음·identify/ping/capabilities 모두 live socket 없음(권한 경계 밖 재확인 동일). 실제 HTTP 터미널 검증으로 진행하며 화면 E2E를 완료로 주장하지 않는다.
