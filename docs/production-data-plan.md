# 운영 충전소 데이터 준비·갱신 구현 계획

> 실행: 이 세션에서 순차적으로 구현한다. agent-engineering, TDD 및 기존 verify-plugpass를 사용한다. 병렬 에이전트는 사용하지 않는다.

## 목표와 승인된 범위

사용자의 `process`는 초기 실데이터 수집, 단일 수집 실행, 주기 갱신·장애 안내, 데이터 보존·백업 검증을 진행하라는 지시다. 2026-10-13 사용자 확인: getChargerInfo와 getChargerStatus 각각 일일100,000회. 키는 기존 운영 비밀 설정을 재사용하며 출력하지 않는다. 실제 전국 정보와 최근 상태 갱신을 제공하고, 미준비/오래됨을 정상 빈 결과나 실시간 보장으로 표시하지 않는다.

## 설계

웹 슬롯은 수집하지 않는다. 배포된 동일 JAR의 일회 실행 모드를 별도 수집 작업으로 실행한다. MySQL 연결 소유 잠금으로 서로 다른 JVM도 중복 쓰기를 거부한다. 외부 요청 동안 DB 트랜잭션을 열지 않고 페이지 단위 commit과 기존 데이터 보존을 유지한다. 운영 스케줄러가 기본 정보 일일 수집, 상태5분 수집을 호출한다. 상태 API의 period는 최대10분이므로10분 겹침을 사용하며 누락 기간은 전체 정보 재동기화로 복구한다. 상태 변경 시각을 관측 시각으로 둔갑시키지 않는다.

기본 정보는 전국(zcode 생략)을 지원한다. 요청·페이지·실행시간 상한을 운영 규모에 맞춰 명시하고 재시도는 기존1회 상한을 유지한다. 공급자 오류/부분 실패/조기 빈 페이지/중복 식별자는 완료로 처리하지 않는다. 삭제·폐쇄는 데이터 삭제 대신 원본 표시를 유지한다. 상태만 수집한 성공은 전체 카탈로그 준비 완료로 취급하지 않는다.

초기 성공·최근 시도·마지막 전체 성공·상태 갱신 성공을 구분한다. 공공API가 내려가도 이전 저장 결과를 계속 제공하고 실패 이력이 성공 시각을 초기화하지 않는다. 기존 dataReady 의미는 호환 유지하고 운영 갱신 상태를 별도로 노출한다.

백업은 기존 운영 MySQL을 명시적으로 포함하고 임시 DB에 복원·건수 확인한다. 운영 DB를 복원 대상으로 사용하지 않는다. 외부 저장소 보관은 현재 구성·권한을 먼저 확인한다. 보관 정책은 일일 백업7일을 시작점으로 실제 스케줄과 복원 결과를 기록한다.

```text
일일 기본정보 / 5분 상태 타이머
  → 일회 실행 JAR → DB 연결 잠금 → 공공 API → 페이지 검증·commit → MySQL
웹 blue/green → 조회 서비스 → MySQL → 준비/갱신 지연 안내 + 충전소 목록
MySQL → 백업 → 별도 임시 DB 복원 → 건수 검증
```

## 검토할 실패 경계

1. 배포 중 서로 다른JVM 동시 수집: DB 잠금·해제 실검증.
2. 5분 타이머 지연이10분 조회 창을 넘는 경우: 기본정보 재동기화, 복구 전 정상 최신 갱신으로 표시 금지.
3. 원본 누락/중복/좌표 오류: 기존 데이터 보존·실패 기록, 임의 성공 처리 금지.
4. 재수집 중 이전 상태가 새 상태를 덮는 경우: 공급자 상태 변경 시각 비교 및 metadata 분리.
5. 백업 파일 생성만 성공한 경우: 별도 MySQL 복원·동일 건수 검증 전 복구 가능 완료 금지.

## 초기 조사

운영 공개 응답 dataReady=false/lastSuccessfulRunAt=null. 배포 compose는 두 슬롯 모두 PLUGPASS_INGESTION_ENABLED=false. 공급자 키는 이전 운영 인증200 기록이 있음. 2026-10-13 VM 읽기 확인: PlugPass green, MySQL8.4 컨테이너 실행 중. 기존 CLI 없음, 원래 AtomicBoolean은 JVM 범위뿐. 실제 구현·실행 결과는 후속 기록으로 구분한다.

## 실행 결과와 미완료 범위
